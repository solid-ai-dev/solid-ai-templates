# ADR-022: Skill authoring is an in-scope artifact type

## Context

The template library governs the agent context files a project ships —
`CLAUDE.md` and `AGENTS.md` — through the output-format spec in
`templates/base/core/agents.md`. It said nothing about a second agent
artifact that projects using this system already author heavily:
skills (`.claude/skills/<name>/SKILL.md`), whose YAML `description`
drives auto-triggering and whose body holds an on-demand procedure.

The library's only prior encounter with skills was an experiment that
authored two locally, judged them redundant with always-loaded context,
and removed them. That outcome is a design lesson worth capturing, not a
reason to leave the topic ungoverned. Downstream projects have many
skills and no shared guidance on when a skill earns its place, how to
write the triggering description, or how to keep one from duplicating
always-loaded rules.

The earlier decision that generation is a user-space concern narrowed
the product to a composable template library. Skill authoring fits that
framing — it is guidance that travels as a template, not a generator —
but it expands the artifact types the library speaks to, so the scope
call is recorded here.

## Decision

Skills are an in-scope artifact type, governed by a dedicated base template kept
separate from the context-file spec, and a skill holds an on-demand procedure that never
restates always-loaded context.

## Rationale

- Downstream projects author many skills with no shared guidance on when a skill earns
  its place, how to write its description, or how to keep it from duplicating
  always-loaded rules.
- The library's own experiment found two skills redundant with always-loaded context, a
  design lesson worth capturing rather than a reason to leave the topic ungoverned.
- Skill guidance travels as a template, not a generator, so it fits the composable
  template library; a doc under `docs/` would never reach a project's resolved chain.

## Design

1. **Skills are in scope** — the library provides authoring guidance for
   `.claude/skills/<name>/SKILL.md` skills as a first-class artifact type
   alongside context files.
2. **A dedicated base template owns it** — `templates/base/core/skills.md`
   (`[ID: base-skills]`) holds the guidance: when to write a skill,
   frontmatter and description rules, body structure with an annotated
   skeleton, progressive disclosure, bundled scripts, and a self-check.
3. **The gate is always-loaded vs on-demand** — a rule that MUST fire on
   every turn belongs in a context file or template; a skill is for a
   reusable procedure loaded only when a task matches. A skill MUST NOT
   restate always-loaded context.
4. **Skill authoring stays separate from the context-file spec** —
   `agents.md` governs always-loaded rules, `skills.md` governs on-demand
   procedures; neither absorbs the other.

## Alternatives considered

- **Leave skills ungoverned** — rejected; downstream projects author
  many skills with no shared quality bar, and the redundancy failure the
  library already hit recurs uncaptured.
- **Add a skills section inside `agents.md`** — rejected; conflates two
  distinct artifact types (always-loaded vs on-demand) in one template
  and inflates a file already scoped to context-file output.
- **A standalone doc under `docs/`** — rejected; guidance in `docs/`
  does not compose into a project's resolved template chain, so it never
  reaches the agents that author skills.

## Consequences

- `templates/manifest.yaml` gains a `base-skills` entry; `docs/SPEC.md`
  base listing is regenerated by `py tools/sync.py`.
- The canonical `base-skills` structure becomes the reference a skills
  self-check verifies against.
- Stack or layer templates MAY reference `base-skills` where a stack
  ships skills, via `[DEPENDS ON: ...]`.
