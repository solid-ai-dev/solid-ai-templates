# Efficacy benchmark, round 4 — 2026-10-17

Round 4 tested the two hypotheses registered in `docs/design/efficacy-benchmark.md`
sections 12.2 to 12.4 before any of its trials ran. This file states their verdicts.
The numbers behind them are the two generated reports beside it:

- [`2026-10-17-efficacy-thin.md`](2026-10-17-efficacy-thin.md): `claude-sonnet-5`,
  `SPEC-thin.md`, build task (#1876)
- [`2026-10-17-efficacy-weaker.md`](2026-10-17-efficacy-weaker.md):
  `claude-haiku-4-5-20251001`, `SPEC.md`, build and change tasks (#1875)

Both runs used round 3's five arms and files, K = 3, and `claude-opus-5-5` as the
only judge, three readings per trial, with no cross-check, as section 12.2 registered.
Their raw data is archived and verified in `braboj/tariff-runs`, under
`rounds/2026-10-16-thin` and `rounds/2026-10-15-weaker`.

## Verdicts

| Hypothesis | Verdict | Rows that count |
|---|---|---|
| 12.3: with a thin spec, the files' gain on security and data protection shows | **Supported** | hybrid on the judge's security row (+1.45); full (+27 pp) and hand (+32 pp) on the security probes |
| 12.4: the files' gap to `none` opens as the model weakens | **Supported** | full on the judge's security row (+0.56); hybrid on the judge's data-protection row (+1.0); hand on the security probes (+18 pp) |

A row counts when an arm's growth over round 3 reaches the row's registered smallest
change that matters, and round 4's contrast against `none` reads "better". Growth is
round 4's mean paired difference against `none`, minus round 3's for the same arm and
row, as `2026-09-27-efficacy.md` prints it. The bars are 0.5 points for a judge row,
9 pp (one probe of eleven) for the security probes, 30 pp for the data-protection
probes, and 5 pp for task success.

Both verdicts rest on a few rows at K = 3, and each report owes an escalation to K = 5
that has not been run. **Task success did not grow for any arm under the weaker
model.** Every file arm but hand scored worse than `none` on the hidden suite: full 0 %,
short 24 %, hybrid 21 %, hand 47 %, against 33 % for `none`.

## The hybrid arm under the thin spec (#1949)

All three thin hybrid trials refuse to start without `TARIFF_SECRET_KEY`. Their
context file forbids a default secret. The round-4 specification named no such
variable, and scoring did not supply one. So every HTTP test errored, and the probes
reached no running application. The registered scores stand: hybrid's build suite is
42 %, its security probes are 32 %, and its data-protection probes are 0 %. Those three
figures measure the missing variable, not the code.

Re-run with the key supplied, the same three trees pass 87.1 %, 94.6 % and 84.8 % of
the hidden suite, against 89 % to 93 % for `none`. The probes were not re-run. The
re-run and its exact command are archived in `rounds/2026-10-16-thin-sensitivity`.
From round 5, the specification names the variable and scoring supplies it (PR #1952).

The judge reads code rather than a running app. It gave hybrid the highest security
(3.33) and data-protection (3.11) scores of any thin arm, and hybrid's security row is
one of the three rows that support 12.3.

Round 3 was not exposed to this gap: every round-3 trial passed at least 99.4 % of the
hidden suite. Rounds 1 and 2 predate sign-in in the specification, and their arm means
were 85 % to 99 %. Whether this cause was behind the lower ones was not checked.

The weaker run's hybrid failures are different. Two of its three trials shipped no
`tariff.create_app`, a fault in the code itself.
