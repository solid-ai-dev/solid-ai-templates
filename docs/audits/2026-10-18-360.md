# 360-Degree Audit — 2026-10-18

Run before cutting `v3.0.0`, the review before a major that #1927 lists. It is
the first audit since the v3.0 split moved stacks, platforms, the interview,
examples and generated chains to forks (ADR-049, ADR-050), so the adopter path
now runs through the first fork, `Imbra-Ltd/imbra-ai-templates`, and the
reviewers read it.

Seven parallel, context-isolated subagents per the fork's
`templates/workflow/360.md`. This is a headless project, so the 360-headless
adaptation applies: Value, Viability and Discovery are light lenses, and Quality
is re-projected into four engineering dimensions with one isolated reviewer
each. Each reviewer was given its own dimension's 2026-09-07 findings and
instructed to reconcile against them rather than re-derive. The overall grade is
the lowest dimension grade.

Mechanical layer before fan-out: smoke 34/34, conformance 11 passed / 0 failed /
2 not applicable, fork sync 3/3, `release_check.py --self-test` 8/8,
`sync --check` and `resolve --check` clean, redundancy 0 exact, 0 open pull
requests, 13 open issues. HEAD `bde8a0f`, 172 commits past `v2.90.0`. The
fixture canary STK-24 ran live the same day from the fork at `492a647` through
the `claude-cli` provider: PASS in 145 s.

One dimension held, six fell. Every fall traces to the split: the engine and

them describe a state between the old repository and the new one.

## The finding that governs the rest

The adopter path is broken across the two repositories. Upstream's README sends
an adopter to the fork's README; all three of the fork's first-run paths clone
or submodule upstream and read a `templates/INTERVIEW.md` upstream no longer
ships. The fork's guided prompt seeds `core:` and drops the five `fork_core:`
templates. The migration guide tells a project to pin a released fork tag, and
the fork has none. Value and Discovery found this independently; every
upstream gate is green over it, because no gate reads the fork's README.

## The contract the release freezes is not enforced

ADR-051 freezes template and section IDs for 3.x and names smoke and the
fork-sync job as the enforcement. A control renamed a section ID only a fork
extends: upstream smoke and fork sync passed, and the fork failed only after
merging. The release procedure has no frozen-surface step, and PLAYBOOK still
describes renaming in place. Separately, a `fork_core` entry's `depends_on` is
checked for existence but never walked into the chain, so a second fork's core
addition loses its dependencies with every gate green.

## Governance

ADR-049 and ADR-050 were edited in place after their first implementation
merged, including a reversed rejected alternative in ADR-050. The owner decided
those edits as pre-release refinements; CLAUDE.md "Decision logs" sets the line
at the first merged implementation, not at the release. Recorded here as a
conflict between practice and rule for the owner to resolve, not as a defect
this audit fixes.

## Current bottleneck

Viability, now measured rather than inferred. The efficacy benchmark exists and
in five reported runs has not shown the templates beating a 39-line
hand-written file; under a weaker model every template arm lowered task success
against no file at all. Adoption is unchanged at 4 stars, 0 watchers and no
issue or pull request from anyone but the owner, while one maintainer now runs
two repositories with no milestone past v3.0. The README's value claim is ahead
of the evidence the project itself produced.

## Method note

Seven isolated reviewers, each with its own context window, its own
dimension's prior findings, and an instruction to verify every finding
adversarially. Testing, Authoring and Architecture ran controls in scratch
copies; each states the control and its before-and-after values. Both real
repositories were left clean. One finding is in work this session produced:
the `release_check.py` self-test case "a skipped version" passes on a
duplicate-section finding, so the SemVer-step branch it names has no test.
