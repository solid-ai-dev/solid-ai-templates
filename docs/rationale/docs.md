# Rationale: docs

Why the rules in `templates/core/docs.md` say what they say. The template
states each rule as one instruction; the reasoning and the worked examples
are here, one heading per section, named by ID where the section has one.

## Rule language

A plain imperative is the commonest way a rule is written, so reading it as
MUST keeps the key words for the cases where strength is the point: a
SHOULD that permits a justified deviation, or a MAY that settles a choice
without discussion.

## Standard documents

The three documents are the minimum an agent and a person need to find
their way in. Their layout is left to the project, because a prescribed
README structure is a rule most projects would decline.

## Single source of truth

A second copy of the directory tree drifts the first time a folder moves,
and nothing says which copy is current. A pointer cannot drift.

## Upkeep

Documentation that goes out of sync is worse than none: a reader trusts it.
Past or future tense in a description of the present usually marks a
sentence written before or after the change it describes.

## Disagreements

A document that contradicts the system is not automatically the authority.
A document generated from a template can drift from the template while the
system still matches it; acting on the document first destroys a correct
configuration to satisfy a sentence that was already stale.

## Adopting shared rules

Templates offer conventions; they do not mandate work. A rule adopted
because a newer version exists, rather than because the project needs it,
turns every upstream release into a compliance backlog. The adoption
boundary is inlined into a reference or hybrid file because such a file
reads upstream live: without it, a new upstream MUST would silently widen
what the project follows.

## Line width

A document is not code and does not inherit the source line limit, so it
gets its own, declared where the linter reads it. A second declaration
drifts from the first and nothing says which won. A project that declares no
width has no rule: near-total compliance kept by hand looks healthy and
decays at the edges with nothing to notice.

An unbreakable token is measured, not the line with the token removed:
removing a link makes most long lines fit, so the second test excuses every
long line that happens to carry one.

## Writing style

A hand-maintained table restating a CLI's `--help` or a generated schema is
a second copy that drifts the moment an option is added. A count about the
tree written into a sentence is right on the day it is typed and wrong the
next time the tree moves, and nothing says so; a generator's block is
rewritten and gated, so it cannot go stale silently.

## docs-cold-reader

A ticket is read by whoever decides to pick the work up, a pull request by
whoever decides to approve it, a defect record by whoever meets the defect
again. None of them has the code in mind, and the author is in the one state
of knowledge the reader never shares: they have just finished the
investigation. An agent needs this written down more than a person does,
because it does not notice its own density, and files a body that is
correct, complete and opaque.

The same fact, written both ways:

```text
Two packets that serialize to identical bytes are NOT reachable as unequal
without an assignment -- the generic and concrete PDUs use different formats
and so produce different bytes for the same values.
```

```text
You have to change a value after creating the packet to run into this.
Nothing in the library does that yet, so no current behaviour is wrong.
```

The first opens with the mechanism, needs a double negative unpacked, and
names two types without saying what they are. Both are accurate; only the
second answers the question its reader arrived with. The rule is judgement,
so it has no gate: a sentence-length check passes prose nobody can follow
and fails a long sentence that reads cleanly.

## Diagrams and assets

An artefact with two authorities in the tree, an editable source and the
generator that produced it, loses work: whoever moves a box in the editor
has it reverted by the next run. Either authority is coherent alone.

## Generated files

Generated files rot in four ways: they are hand-edited, their source moves
without a refresh, a formatter touches them at commit time, or they are
produced by a different invocation than the documented one. The last
defeats review. An export committed at half the documented scale renders
every arrow correctly, and the smaller file reads in the diffstat as a
compression win, so every signal a reviewer has points the wrong way; only
a re-render catches it.

A banner looks like this:

```markdown
<!-- Generated by `python3 tools/generator.py`. Edit the source
     (path/to/source.yaml) or the renderer, not this file. Run
     `python3 tools/generator.py --check` to verify the committed
     file is up to date. -->
```

A generator with a hardcoded field list fails both ways at once: it renders
dead columns for fields the data lacks, and silently omits fields it has.
